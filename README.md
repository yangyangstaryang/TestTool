# Embodied Eval Kit —— 具身智能任务评测与轨迹回放工具

> 这是你的**第一个具身智能作品**。纯 Python 标准库，零第三方依赖、零硬件、零 GPU、零 ROS2 环境，Windows 上直接能跑。
> 它对应具身智能公司本科可投的「**模型评测工程师 / 数据工具链 / 机器人软件工程师**」岗位。

## 一、先跑起来（3 分钟）

打开终端（VSCode 里按 `` Ctrl + ` `` 也行），逐行执行：

```bash
cd G:/MY/research/embodied-ai-starter
python evaluate.py --self-test
python evaluate.py --input sample_data --output report.html
```

第一条会打印 `[OK] 全部自测通过...`；第二条会打印成功率和 P95 延迟，并在当前目录生成 `report.html`。

**双击打开 `report.html`**，你会看到：整体成功率、按任务/策略分组的对比、失败归因、延迟 P50/P95/P99、自动生成的结论、逐条 episode 明细。

再试一下按策略分组（看不同模型的表现差异）：

```bash
python evaluate.py --input sample_data --group-by policy --output by_policy.html
```

> 如果 `python` 命令无效，试 `py` 或 `python3`。需要 Python 3.7+。

## 二、这个工具在解决什么真实问题

机器人跑一次任务（抓个杯子、插个零件、走一段走廊）会留下一条日志。公司里真实的痛点是：

- 一次跑 200 个 episode，人工翻日志根本看不过来
- "模型成功率 60%" 太笼统——**到底失败在哪一步？是看错了、规划错了、还是手滑了？**
- 平均延迟正常，但偶发一次 200ms 卡顿，真机上就可能撞东西

这个工具就是干这个的：把日志变成一份能直接拿去开会的评测报告。这也是为什么 JD 里反复出现"**设计评测方案、日志分析、数据回放、问题定位、自动化测试**"。

## 三、数据格式（改数据是最容易的第一次练手）

打开 `sample_data/episodes.json`，它是一个数组，每个元素是一次任务记录：

| 字段                   | 含义                 | 示例                                              |
| ---------------------- | -------------------- | ------------------------------------------------- |
| `episode_id`           | 编号                 | `"pp_001"`                                        |
| `task`                 | 任务类型             | `pick_place` / `insertion` / `navigation`         |
| `scene`                | 场景                 | `table_A` / `corridor`                            |
| `policy`               | 用的模型/策略版本    | `vla_v2` / `bc_baseline`                          |
| `success`              | 是否成功             | `true` / `false`                                  |
| `steps` / `duration_s` | 步数 / 耗时          | `38` / `7.6`                                      |
| `failure_stage`        | 失败发生在哪个阶段   | `perception` / `planning` / `control` / `timeout` |
| `failure_reason`       | 具体失败原因         | `grasp_slip` / `perception_miss` / `collision`    |
| `latency_ms`           | 每步控制延迟（毫秒） | `[11,12,13,...]`                                  |

**改数据不用改代码**：往数组里加几条 episode，重新跑一次命令，报告就变了。这就是"数据驱动评测"最朴素的样子。

## 四、代码怎么读（按这个顺序，别从头硬啃）

打开 `evaluate.py`，它被分成三层，注释里也标了：

1. **`load_episodes()`** —— 加载数据、补默认值、做基本校验。支持 `.json` 和 `.jsonl`。
2. **`summarize()` / `group_by()` / `failure_breakdown()` / `build_insights()`** —— 指标计算。核心是 `percentile()`（最近秩分位数）和 `build_insights()`（自动写结论）。
3. **`render()`** —— 把指标拼成 HTML 报告，CSS 在文件里的 `CSS` 常量。

**为什么要分层**（面试要点）：以后把第 1 层换成"读 ROS2 bag"或"读 LeRobot 数据集"的适配器，第 2、3 层一行都不用改。这叫**可替换的数据接入层**，是工具链岗最看重的设计意识。

3. 加一个新指标：比如"成功 episode 的平均步数 vs 失败 episode 的平均步数"（提示：在 `summarize()` 里加，在 `render()` 的卡片区显示）

5. 用 Git 管理起来，每次改动都提交，commit message 写清楚改了什么：


**面试高频追问，先想好答案**：

| 问题                              | 要点                                                                                 |
| --------------------------------- | ------------------------------------------------------------------------------------ |
| 为什么报 P95/P99 而不是平均延迟？ | 机器人控制是实时系统，长尾卡顿才会导致真机事故；平均值会把它抹平                     |
| 失败归因怎么分类才不重不漏？      | 先按阶段分（感知/规划/控制/超时）保证互斥，再在阶段内细化原因                        |
| 分位数用什么口径？                | 最近秩法，说明索引计算，数据量小时和线性插值的差异                                   |
| 怎么接真实机器人？                | 订阅 ROS2 topic → 转成 episode 格式；或把 LeRobot dataset 字段映射过来，只改 load 层 |
| 这个工具的局限？                  | 只看离线日志，覆盖不了硬件故障和在线抖动，需要在线监控/告警补充                      |
| 遇到最大的坑是什么？              | **如实讲你自己改代码时遇到的那个**，别背答案                                         |

## 八、文件结构

```
embodied-ai-starter/
├── README.md                 ← 你正在读的
├── evaluate.py               ← 主程序（load / metrics / render 三层）
├── sample_data/
│   └── episodes.json         ← 20 条示例 episode（3 任务 / 3 策略 / 8 失败）
├── report.html               ← 运行后生成
└── by_policy.html            ← 换分组维度后生成
```

无需 `pip install`。没有 requirements.txt，因为**一个第三方包都没用**——这是刻意的，让你第一天就能跑起来，而不是先跟环境搏斗两小时。
